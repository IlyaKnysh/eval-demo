# Automation Framework Issues

**Scope:** `.claude/skills/automation-framework-review-skill-creator/evals/fixtures/clean-framework` (Storefront Admin E2E, TypeScript + Playwright Test). All 30 files were read in full: 15 source files under `src/`, 5 spec files (15 tests) under `tests/`, plus config, CI workflow, README and CONTRIBUTING.
**Excluded from this review:** nothing. The framework was not executed, so runtime claims about the app under test are marked as hypotheses where they apply.

**Verdict up front:** Two things should block sign-off. First, five of the 15 tests have titles that promise behavior their assertions never check. "Supports adding custom notes" never enters a note, and the multi-item order path probably never adds a second item. Second, no lockfile is committed, so both CI jobs fail at `npm ci` before a single test runs. The rest are small fixes: a discouraged `networkidle` wait on every navigation, login that never confirms it succeeded, preconditions built through the UI even though an API is available, and a few minor duplications and gaps.

---

## Five tests assert less than their titles claim; two never exercise the feature they name `[Impact: High | Effort: Medium]`

A count of assertion-free tests gives **0 of 15**, because every test calls at least one `expect*` method. But **5 of 15** check only that a grid row exists, never the specific behavior in the test's title:

| Test | Title promises | What actually runs / is checked |
|---|---|---|
| `tests/orders/createOrder.spec.ts:41-48` | "supports adding custom notes to a new order" | `buildOrder({ notes: ... })` sets `notes`, but `OrderModifyPage.fillFromOrderData` (`src/pages/OrderModifyPage.ts:41-48`) fills customer, status and items only. **Notes are never typed into the UI**, and the test asserts only `expectRowWithCustomer`. It would still pass if the notes field were removed from the app. `OrderBuilder.withNotes` (`orderFactory.ts:67`) has 0 callers. |
| `tests/orders/createOrder.spec.ts:23-30` | "creates a multi-item order" | `addLineItem` (`OrderModifyPage.ts:35-39`) refills the same `getByLabel('SKU')` / `getByLabel('Quantity')` fields and never triggers an "add row" action. With a single SKU input, the second item overwrites the first. With one input per row, `getByLabel('SKU')` fails Playwright's strict mode (it matches more than one element). *(Which of the two happens depends on the panel's markup; verify against the app.)* Either way, the assertion (row exists) cannot tell. |
| `tests/orders/createOrder.spec.ts:32-39` | "creates an order with a custom initial status" | Status `processing` is selected but never read back. Only row presence is asserted. |
| `tests/users/registerUser.spec.ts:19-26` | "registers a new admin user" | The role is never read back. Only row presence is asserted. |
| `tests/users/registerUser.spec.ts:28-35` | "registers a new read-only user" | Same as above. |

Taken together, these three create-order and two registration tests check the same thing as their smoke-tagged siblings and add no coverage beyond them. The repo already has the right pattern in `tests/orders/updateOrderStatus.spec.ts:16-17` and `tests/users/changeUserRole.spec.ts:16-17`: reopen the record and assert the field value (`expectStatusFieldValue` / `expectRoleFieldValue`). Apply it to these five tests. Notes needs a `fillNotes` step in `fillFromOrderData` plus an `expectNotes` method. Multi-item needs `addLineItem` to drive the panel's real add-row control and an assertion on line-item count or total.

## No lockfile committed; `npm ci` fails in both CI jobs `[Impact: High | Effort: Low]`

`.github/workflows/e2e-tests.yml:27` (smoke) and `:65` (full regression) both run `npm ci`. `npm ci` aborts when there is no `package-lock.json`, and the tree has none: `ls package-lock.json yarn.lock pnpm-lock.yaml` finds no such file, and `.gitignore` does not exclude one. As committed, neither the PR gate nor the nightly run gets past dependency install. Without a lockfile, `"@playwright/test": "^1.47.2"` (`package.json:16`) also resolves to whatever the newest 1.x is at install time, so local and CI runs are not reproducible. Fix: commit the `package-lock.json` generated by `npm install`. *(If the lockfile exists upstream and was only left out of the copy reviewed here, drop this finding.)*

## Every navigation waits on the discouraged `networkidle` state `[Impact: Medium | Effort: Low]`

Grep for unconditional sleeps (`waitForTimeout|setTimeout|sleep|implicitlyWait`): **0 hits**. The one non-web-first wait is `BasePage.waitForLoad()` → `page.waitForLoadState('networkidle')` (`src/core/BasePage.ts:18`). It is called from 3 sites (`DashboardPage.ts:35`, `DashboardPage.ts:42`, `LoginPage.ts:50`), so it runs on every login and every `goToOrders`/`goToUsers`. That means all 15 tests depend on it. Playwright's own docs mark `networkidle` as discouraged for testing. If the admin app polls, streams over a websocket or sends analytics beacons, the wait hangs until the 10 s `actionTimeout`/30 s test timeout. It can also return before client-side rendering finishes. The rest of the framework already waits correctly with web-first assertions (`LoginPage.open` at `LoginPage.ts:36`, `EntityModifyPanel.waitForOpen` at `EntityModifyPanel.ts:37`). Replace `waitForLoad()` with a per-page readiness assertion, e.g. `expect(welcomeBanner).toBeVisible()` for the dashboard and `expectGridVisible()` for list pages.

## Login never confirms it succeeded, and missing credentials fall back to placeholders `[Impact: Medium | Effort: Low]`

`adminUser()` / `standardUser()` fall back to literal placeholders when the env vars are unset (`src/factories/userFactory.ts:68-69`, `:78-79`: `'admin.qa@example.com'` / `'replace-me'`). `LoginPage.loginAs` (`LoginPage.ts:44-53`) then returns a `DashboardPage` after the `networkidle` wait from the previous finding, without checking that the dashboard actually loaded. So a run with a missing or rotated secret does not fail at login. The `adminSession` fixture (`src/core/fixtures.ts:55-58`) reports success, and each of the 12 of 15 tests that use it fails later. The error is something like a click timeout on the `Orders` nav link, wrapped as "Creating order for …", which points triage at the order feature. This shares its trigger with the `networkidle` finding but needs its own fix. Throw on a missing `ADMIN_*`/`STANDARD_*` env var instead of falling back, and have `loginAs` assert a dashboard element, which `expectWelcomeVisible` already provides at `DashboardPage.ts:28-30`, before returning.

## Test preconditions are built through the UI even though an API is in use `[Impact: Medium | Effort: Medium]`

The 3 tests in `updateOrderStatus.spec.ts` and the 2 in `changeUserRole.spec.ts` create their starting record by running the full UI create flow (`createOrder` / `registerUser`), and only then exercise the behavior under test. That makes those 5 tests slower and fail them when the create UI is broken, not when update or role-change is broken. The framework already calls the backend directly for teardown (`page.request.delete('/api/orders…')` at `fixtures.ts:88`, `'/api/users/…'` at `fixtures.ts:99`), so API seeding is within reach. `.env.example:13-14` also documents `API_BASE_URL` as "used by factories" for "direct test-data seeding calls", but a grep finds **0 references** to `API_BASE_URL` in code or CI. The documented mechanism does not exist. A related point to verify: cleanup uses relative URLs, which resolve against `BASE_URL` (the UI host), while `.env.example` documents a separate API host. That works only if the UI host proxies `/api`. Add API-backed `seedOrder`/`seedUser` helpers next to the cleanup calls and use them for Arrange in tests whose subject is not creation.

## Order and user grid lookups probably only see the first page of results (to be verified) `[Impact: Medium | Effort: Low]`

`OrderListPage` and `UserListPage` describe themselves as "paginated" grids (`OrderListPage.ts:7`, `UserListPage.ts:7`). Every row lookup goes through `getUniqueGridRow` (`src/utils/gridUtils.ts:22-35`), which searches only the rendered rows and times out if the record is not on the current page. That affects 12 of 15 tests: all order and user tests through `expectRow*`/`open*By*`, and the `updateOrderStatus`/`changeUserRole` flows. `OrderListPage.searchFor` (`OrderListPage.ts:31-34`) would narrow the grid first, but it has **0 callers**, and `UserListPage` has no search method. If the grid's default sort does not put newest records first, results will depend on how much data has built up in the shared staging environment. Confirm the default sort. If it is not newest-first, run a search before every lookup.

## Cleanup teardown stops at the first failed delete `[Impact: Low | Effort: Low]`

`createdRecords` teardown (`fixtures.ts:71-76`) awaits each delete in sequence, and `deleteOrder`/`deleteUser` throw on any non-2xx response (`:91-93`, `:102-104`). One failed delete skips the remaining orders and every registered user. Today each test registers exactly 1 record, so the leak is at most one record per test. The record is also registered *before* it is created (e.g. `createOrder.spec.ts:14`). A test that fails before Save will therefore try to delete a record that does not exist, and if that endpoint returns 404 for no match, teardown adds a second error on top of the real failure. Run every delete, collect the errors, throw once at the end, and treat 404 as "nothing to clean".

## The `nextSuffix()` ID generator is copy-pasted between the two factories `[Impact: Low | Effort: Low]`

`src/factories/orderFactory.ts:3-16` and `src/factories/userFactory.ts:3-16` hold identical copies (same body, same doc comment) of the worker-safe unique-suffix generator, each with its own `sequence` counter. The two copies are correct now but will drift on the next edit. Move it to `src/utils/uniqueId.ts`.

## The login sequence is duplicated between the fixture and the auth flow `[Impact: Low | Effort: Low]`

`fixtures.ts:80-84` (`loginAs`) repeats `authFlows.ts:12-14` (`new LoginPage` → `open()` → `loginAs(user)`). The fixture cannot reuse `loginAsUser` because the flows import `test` from `@core/fixtures` only to call `test.step` (`authFlows.ts:1`, `orderFlows.ts:1`, `userFlows.ts:1`), so the dependency would be circular. Fix: have the flows import `test` from `@playwright/test` (`test.step` behaves the same), then let the `adminSession` fixture call `loginAsUser`.

## The negative-login path contradicts the "never log in with a raw credential string" rule `[Impact: Low | Effort: Low]`

`CONTRIBUTING.md:60-62` and the comment at `LoginPage.ts:42` ("No test bypasses this with a raw credential string") state there are no exceptions. Yet `tests/auth/login.spec.ts:26` passes `'nobody@example.com'` / `'wrong-password'` through `attemptInvalidLogin(page, email, password)` (`authFlows.ts:20`) into `LoginPage.submitLoginAttempt(email, password)` (`LoginPage.ts:60`). So the suite has two ways to express the same login concept. This is the only such call site (1 of 3 login tests). Either write the exception into the rule, or have `attemptInvalidLogin` take a `User` built with `buildUser({ password: 'wrong-password' })`.

## No linter gate, so a missing `await` would go unnoticed `[Impact: Low | Effort: Low]`

The baseline used for this check is the `CONTRIBUTING.md` naming table plus `tsconfig.json` `"strict": true`. CI enforces type checking (`e2e-tests.yml:29-30`, `:67-68`), but the repo has no ESLint or Prettier config (0 `.eslintrc*`/`eslint.config.*`/`.prettierrc*` files), and `package.json:15-19` lists only `@playwright/test`, `@types/node` and `typescript`. CONTRIBUTING.md:3 says the naming rules are "enforced by convention and PR review". Naming currently complies: 6 of 6 page objects end in `Page`, 5 of 5 test files end in `.spec.ts`, 2 of 2 factories follow `<entity>Factory.ts`, and all 6 flow functions are verb phrases. The real risk is that `tsc --strict` does not catch a forgotten `await` on a Playwright call, which is the classic way a Playwright test passes without checking anything. Add `@typescript-eslint/no-floating-promises` (plus Playwright's `eslint-plugin-playwright`) to the CI type-check step.

## Unused public members and one stale doc comment `[Impact: Low | Effort: Low]`

Repo-wide grep finds 0 references outside the definition for: `OrderListPage.searchFor` (`OrderListPage.ts:31`), `OrderModifyPage.cancel` (`OrderModifyPage.ts:54`), `UserModifyPage.cancel` (`UserModifyPage.ts:50`), `OrderBuilder.withCustomer` (`orderFactory.ts:51`), `OrderBuilder.addItem` (`:62`) and `OrderBuilder.withNotes` (`:67`). That is 6 members. Two of them are evidence for findings above (`searchFor` for pagination, `withNotes` for the notes test). Use them there or delete them. Separately, `gridUtils.ts:5-6` says the helper is used by `OrderModifyPage`/`UserModifyPage`. Its actual callers are `OrderListPage.ts:37,49` and `UserListPage.ts:28,40`.

## Noted trade-off (not a defect)

- Page-object actions use `expect()` internally as synchronization or postconditions: `LoginPage.open` (`LoginPage.ts:36`), `EntityModifyPanel.save` (`EntityModifyPanel.ts:62-63`, asserts the "Saved successfully" toast) and `cancel` (`:69`). This is idiomatic Playwright and fine today. It does mean `save()` cannot be reused by a future "save is rejected by validation" test, which will need a separate `submitExpectingError()`-style method rather than an edit to `save()`.

## Recommended actions, in priority order

1. **Commit `package-lock.json`.** Both CI jobs currently fail at `npm ci`. `[High | Low]`
2. **Make the 5 over-claiming tests assert what their titles say.** Reopen the record and assert notes, line items, status and role, using the pattern in `updateOrderStatus.spec.ts:16-17`. Wire `notes` into `fillFromOrderData` and fix `addLineItem` to add a real row. `[High | Medium]`
3. **Replace `waitForLoadState('networkidle')`** with per-page web-first readiness assertions. `[Medium | Low]`
4. **Fail fast on missing credential env vars, and have `loginAs` assert the dashboard loaded.** `[Medium | Low]`
5. **Confirm the grid's default sort.** If it is not newest-first, search before every `getUniqueGridRow` lookup (use the existing `searchFor`; add the same for users). `[Medium | Low]`
6. **Seed preconditions through the API** for the 5 update and role-change tests, and either implement or remove the `API_BASE_URL` described in `.env.example`. `[Medium | Medium]`
7. **Make cleanup teardown attempt every delete** and treat 404 as "nothing to clean". `[Low | Low]`
8. **Extract `nextSuffix()`** into one shared utility. `[Low | Low]`
9. **Remove the fixture's duplicate login sequence.** Have the flows import `test` from `@playwright/test` so `adminSession` can call `loginAsUser`. `[Low | Low]`
10. **Resolve the raw-credential negative-login exception**, either by documenting it or by passing a built `User`. `[Low | Low]`
11. **Add an ESLint gate with `no-floating-promises`** to CI. `[Low | Low]`
12. **Use or delete the 6 unused public members**, and fix the stale `gridUtils.ts` doc comment. `[Low | Low]`
